# מרפא · Marpe

מערכת ניהול קליניקה לרפואה סינית — דו-לשונית (עברית ואנגלית), עם דשבורד מודולרי
וניהול מלאי צמחים.

A bilingual (Hebrew/English) clinic management system for Traditional Chinese
Medicine practice, with a customisable dashboard and real herb inventory tracking.

---

## התקנה · Setup

### 1. דרישות מוקדמות

- Node.js 20.9 ומעלה
- pnpm 9

```bash
pnpm install
```

### 2. יצירת פרויקט Supabase

1. נכנסים ל־[supabase.com](https://supabase.com) ויוצרים פרויקט חדש (התוכנית החינמית מספיקה).
2. בוחרים אזור באירופה (Frankfurt) — קרוב לישראל ומיושר ל־GDPR.
3. שומרים את סיסמת מסד הנתונים.

### 3. הרצת המיגרציות

בעורך ה־SQL של הפרויקט, מריצים את הקבצים מתיקיית `supabase/migrations`
**לפי הסדר** (שם הקובץ קובע את הסדר):

```
20260906090000_init_tenancy.sql
20260906090050_audit.sql
20260906090100_patients.sql
20260906090200_scheduling.sql
20260906090300_clinical_notes.sql
20260906090400_inventory.sql
20260906090500_dispensing.sql
20260906090600_dashboard_layouts.sql
20260906090700_patient_portal.sql
```

לחלופין, עם ה־CLI של Supabase:

```bash
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

### 4. יצירת המשתמש הראשון והרצת ה־seed

1. ב־Supabase: **Authentication → Users → Add user**, עם אימייל וסיסמה.
2. בעורך ה־SQL מריצים את `supabase/seed.sql`.

ה־seed יוצר את הקליניקה, הופך את המשתמש הראשון לבעלים, מגדיר שעות עבודה
(ראשון–חמישי, 09:00–17:00), ומוסיף סוגי טיפול, כ־28 צמחים נפוצים וארבע נוסחאות
קלאסיות.

### 5. הזנת המפתחות

```bash
cp apps/web/.env.example apps/web/.env.local
cp apps/portal/.env.example apps/portal/.env.local
```

ממלאים בשני הקבצים את `NEXT_PUBLIC_SUPABASE_URL` ואת
`NEXT_PUBLIC_SUPABASE_ANON_KEY` מתוך **Settings → API**.

### 6. הרצה

```bash
pnpm dev
```

- אפליקציית הצוות: <http://localhost:3000>
- פורטל המטופלים: <http://localhost:3001>

בלי מפתחות האפליקציה עדיין עולה ומציגה מסך הסבר בכתובת `/he/setup`.

### למה שתי אפליקציות נפרדות

מטופל וצוות לא חולקים אף מסך. הפרדה ברמת האפליקציה אומרת שרכיב שמיועד לצוות
פשוט לא קיים ב־bundle של המטופל, במקום להסתמך על בדיקת הרשאה שאפשר לשכוח.

## עקרונות שכדאי להכיר לפני שמשנים קוד

**1. כל טבלה מסומנת ב־`clinic_id` ומוגנת ב־RLS.**
גם היום, עם קליניקה אחת. זה מה שיאפשר בעתיד להפוך את המערכת ל־SaaS רב־קליניקות
בלי לכתוב מחדש את מודל הנתונים — וזה מה שמונע מבאג בקוד לחשוף רשומות רפואיות.

**2. לוגיקה קריטית יושבת במסד הנתונים, לא בלקוח.**
מניעת חפיפת תורים היא exclusion constraint. קיזוז מלאי הוא פונקציית
`dispense_formula` שרצה בטרנזקציה אחת ומתגלגלת אחורה במלואה אם חסר מלאי.
בדיקה בצד הלקוח הייתה מוסיפה חלון מרוץ בלי להוסיף ביטחון.

**3. מלאי הוא יומן, לא מספר.**
`stock_movements` היא טבלה append-only. `herb_batches.quantity_remaining` הוא רק
מטמון שמתעדכן ב־trigger. תיקון טעות נעשה בתנועה מקזזת, לא בדריסה — כך שאפשר
תמיד לשחזר את ההיסטוריה, וכך שחיוב עתידי יוכל להסתמך על עלות אמיתית.

**4. RTL הוא ארכיטקטורה, לא תיקון בסוף.**
משתמשים אך ורק במחלקות לוגיות של Tailwind (`ms-*`, `me-*`, `ps-*`, `pe-*`,
`text-start`, `start-*`, `end-*`) — לעולם לא `ml-`/`mr-`/`left-`/`right-`.
שדות טלפון, ת״ז, אימייל, תאריך ושעה מקבלים `dir="ltr"` מפורש (רכיב `LtrInput`),
אחרת הספרות מוצגות בסדר הפוך בתוך עמוד עברי.

**5. הוספת רכיב לדשבורד לא נוגעת בדשבורד.**
כותבים קומפוננטה, קוראים ל־`registerWidget()`, מוסיפים import אחד ב־
`features/dashboard/widgets/index.ts`. הגריד והשמירה לא משתנים.

## פרטיות ורגולציה

המערכת מחזיקה מידע רפואי. הצד ההנדסי מכוסה: הצפנה בתעבורה ובמנוחה (ברירת מחדל
ב־Supabase), הרשאות ברמת השורה, ויומן ביקורת (`audit_log`) שנכתב ב־trigger ולא
ניתן לזיוף מקוד האפליקציה.

**הצד המשפטי הוא מסלול נפרד.** חוק הגנת הפרטיות בישראל, כולל תיקון 13 שנכנס
לתוקף באוגוסט 2025, מטיל חובות על מאגרים המכילים מידע רפואי. מומלץ לוודא את
חובות הרישום והציות מול עורך דין או יועץ פרטיות **לפני** הזנת נתוני מטופלים
אמיתיים.

## מה עוד לא נבנה

Milestone 1 מכסה את הליבה הקלינית בלבד. השלבים הבאים, לפי סדר:

1. **חיוב וקבלות** — כולל אינטגרציה לחשבוניות ישראליות. עמודות העלות כבר קיימות
   ב־`dispensing_items` ומאוכלסות היום, כך שלא יידרש migration.
2. **קביעת תור עצמאית** בפורטל — הסכימה כבר תומכת.
3. **תזכורות** בוואטסאפ ובמייל.
4. **טפסי קליטה** דיגיטליים.
5. **דוחות** — ייכנסו כרכיב חדש באותה מסגרת דשבורד.
6. **ריבוי מטפלים והרשאות** — `memberships.role` כבר קיים.
