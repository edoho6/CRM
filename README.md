# הרבליסט · Herbalist

מערכת ניהול קליניקה לרפואה סינית — דו-לשונית (עברית ואנגלית): תיק מטופל, יומן, טיפול,
מלאי צמחים, מאגר מידע מקצועי, הודעות אוטומטיות, חיוב, פורטל מטופלים ואפליקציות לחנויות.

A bilingual (Hebrew/English) clinic management system for Traditional Chinese Medicine
practice: patient files, diary, treatment records, herb inventory, a professional
reference library, automated messaging, billing, a patient portal and store apps.

## התקנה · Setup

### 1. דרישות מוקדמות

- Node.js 20.9 ומעלה
- pnpm 9

```bash
pnpm install
```

### 2. יצירת פרויקט Supabase

1. נכנסים ל־[supabase.com](https://supabase.com) ויוצרים פרויקט חדש.
2. בוחרים אזור באירופה (Frankfurt) — קרוב לישראל ומיושר ל־GDPR.
3. שומרים את סיסמת מסד הנתונים.

### 3. הרצת המיגרציות

`supabase/migrations/` הוא מקור האמת. מריצים את כל הקבצים **לפי סדר השם** (חותמת הזמן
בתחילת השם קובעת), בעורך ה־SQL של הפרויקט או עם ה־CLI:

```bash
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

בעבודה שוטפת כל מיגרציה חדשה מקבלת גם עותק ממוספר בשורש (`NN_<שם>_to_run.sql`, לא ב־git)
שנועד להדבקה בעורך ה־SQL. אחרי מיגרציה שמוסיפה טבלה או policy מריצים את
`supabase/tests/tenant_isolation.sql` — הבדיקה בונה נתונים בטרנזקציה ומסיימת ב־`rollback`.

### 4. המשתמש הראשון, ה־seed והקטלוגים

1. ב־Supabase: **Authentication → Users → Add user**, עם אימייל וסיסמה.
2. בעורך ה־SQL מריצים את `supabase/seed.sql`: יוצר את הקליניקה, הופך את המשתמש הראשון
   לבעלים, מגדיר שעות עבודה, סוגי טיפול, קטלוג צמחים התחלתי וארבע פורמולות.
3. הקטלוגים המלאים — 376 צמחים, 170 פורמולות ו־361 נקודות דיקור — נמצאים ב־`supabase/seed/{herbs,formulas,points}`.
   `node scripts/bundle-seeds.mjs` אורז אותם לשני קבצים (`2_herbs_and_formulas_to_run.sql`,
   `3_points_to_run.sql`) שמריצים פעם אחת בעורך ה־SQL; הם ממלאים את הקטלוג המשותף של המערכת.
   כל קליניקה מעתיקה אותו לרשימות שלה בלחיצה על "טעינת הקטלוג" בהגדרות ← "מאגר המידע", וקליניקה
   חדשה מקבלת אותו לבד ביום שהיא נוצרת.
   מאגר הרפואה המערבית נטען בסקריפט (`scripts/medicine/README.md`).

### 5. הזנת המפתחות

```bash
cp apps/web/.env.example apps/web/.env.local
cp apps/portal/.env.example apps/portal/.env.local
```

ממלאים בשני הקבצים את `NEXT_PUBLIC_SUPABASE_URL` ואת `NEXT_PUBLIC_SUPABASE_ANON_KEY`
מתוך **Settings → API**. שאר המפתחות (העוזר, הספרייה, סליקה) מתועדים ב־`.env.example`
וב־`DEPLOY.md`; בלעדיהם המסכים המתאימים אומרים שהשירות עדיין לא הופעל, ושאר המערכת עובדת.

### 6. הרצה

```bash
pnpm dev
```

- אפליקציית הצוות: <http://localhost:3000>
- פורטל המטופלים: <http://localhost:3001>

בלי מפתחות האפליקציה עדיין עולה ומציגה מסך הסבר בכתובת `/he/setup`.

### למה שתי אפליקציות נפרדות

מטופל וצוות לא חולקים אף מסך. הפרדה ברמת האפליקציה אומרת שרכיב שמיועד לצוות
פשוט לא קיים ב־bundle של המטופל, במקום להסתמך על בדיקת הרשאה שאפשר לשכוח.

## עקרונות שכדאי להכיר לפני שמשנים קוד

**1. כל טבלה מסומנת ב־`clinic_id` ומוגנת ב־RLS.**
גם היום, עם קליניקה אחת. זה מה שיאפשר להפוך את המערכת ל־SaaS רב־קליניקות בלי לכתוב
מחדש את מודל הנתונים — וזה מה שמונע מבאג בקוד לחשוף רשומות רפואיות. היוצאות מן הכלל
הן טבלאות שהן עובדה אחת לכל השירות (מחירי חנויות, רפואה מערבית, הספרייה).

**2. לוגיקה קריטית יושבת במסד הנתונים, לא בלקוח.**
מניעת חפיפת תורים היא exclusion constraint. קיזוז מלאי הוא פונקציית `dispense_formula`
שרצה בטרנזקציה אחת. רשומה חתומה נעולה ב־trigger. בדיקה בצד הלקוח הייתה מוסיפה חלון
מרוץ בלי להוסיף ביטחון.

**3. מלאי הוא יומן, לא מספר.**
`stock_movements` היא טבלה append-only. `herb_batches.quantity_remaining` הוא רק מטמון
שמתעדכן ב־trigger. תיקון טעות נעשה בתנועה מקזזת, לא בדריסה.

**4. RTL הוא ארכיטקטורה, לא תיקון בסוף.**
רק מחלקות לוגיות של Tailwind (`ms-*`, `me-*`, `ps-*`, `pe-*`, `text-start`) — לעולם לא
`ml-`/`mr-`/`left-`/`right-`. טלפון, ת״ז, אימייל ופינין מקבלים `dir="ltr"` מפורש.

**5. הוספת רכיב לדשבורד לא נוגעת בדשבורד.**
כותבים קומפוננטה, קוראים ל־`registerWidget()`, מוסיפים import אחד ב־
`features/dashboard/widgets/index.ts`.

## פרטיות ורגולציה

המערכת מחזיקה מידע רפואי. הצד ההנדסי מתואר ב־`SECURITY.md`: הצפנה בתעבורה ובמנוחה,
הרשאות ברמת השורה, יומן ביקורת שנכתב ב־trigger וצפייה שנרשמת מהאפליקציה, ניטור גישה חריגה.

**הצד המשפטי הוא מסלול נפרד.** חוק הגנת הפרטיות, כולל תיקון 13 שנכנס לתוקף באוגוסט 2025,
מטיל חובות על מאגרים המכילים מידע רפואי. `GO-LIVE.md` מונה מה חייבים לסגור, ועם מי,
**לפני** הזנת נתוני מטופלים אמיתיים.

## מה עוד לא בנוי

1. **חשבוניות ברמת השוק** — סוגי מסמכים, שליחה, ייצוא לרו״ח, וחיבור לתוכנת החשבוניות של
   המטפל (Morning, iCount, EZcount) דרך ה־API שלהן.
2. **WhatsApp ישירות מול Meta** — חיבור של כל מטפל למספר שלו מתוך המערכת (Tech Provider);
   היום השליחה עוברת דרך 019 או דרך Make + ManyChat של המטפל.
3. **שירות עצמי למטופל** — ביטול ושינוי תור מהקישור, רשימת המתנה.
4. **ייבוא מטופלים** ממערכת קודמת.
5. **הרשאות לפי תפקיד** — היום כל התפקידים רואים אותו דבר, ורק בעלים מנהלים צוות.
6. **טעינת הקטלוגים לקליניקה חדשה מתוך האפליקציה**, ושמות בעברית לצמחים, לפורמולות ולנקודות.
7. **סנכרון דו־כיווני עם יומן גוגל** ויומן מרובה מטפלים.
